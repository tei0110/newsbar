# newsbar 設計書

- 作成日: 2026-10-26
- 状態: レビュー済みドラフト（ユーザーの最終承認待ち）
- `newsbar` は仮の名前。変更可。

この文書では、ユーザーが決めたことを **【決定】**、設計者（Claude）が判断したことを **【判断】** と書き分ける。【判断】の項目はユーザーがまだ明示的に承認していないので、異論があれば変えてよい。

## 1. 何を作るか、なぜ作るか

AI・セキュリティ関連の情報収集を、サイトを一つずつ巡回せずに済ませるための **Macのメニューバー常駐アプリ**。

ユーザーは現在、Simon Willisonのブログ（simonwillison.net）、各AI企業の公式ブログ、ブログやニュースサイトを手で巡回している。読んだ情報は基本的に自分で読んで終わりで、共有や記録はしていない。

ゴールは、**アプリを開いたときに「新しいニュースのまとめ（AIによる日本語の要約）＋元記事へのリンク」が並んでいて、それを読めばその日の情報収集が終わる状態**。

## 2. 目的（優先順位順）【決定】

1. **自分の情報収集が楽になる**: 毎朝、実際に使えること
2. **Rustの勉強になる**: アプリの中身はできるだけRustで書く
3. **ポートフォリオになる**: GitHubで見せられる品質にする
4. **うまくいけば収益化する**: 初版に課金の仕組みは入れない。ただし、後から有料化できない作りは避ける

## 3. 初版でやらないこと（非ゴール）

- スマホアプリ【決定: 最初はMacのみ。将来の拡張候補】
- RSSを出していないサイトのページを直接読み取ること【決定: 後の版に回す。Anthropic・Meta AI・Microsoft AI Blog・Mistralは初版の対象外。Anthropicの発表はSimon WillisonやHacker Newsが取り上げることで当面カバーする】
- テーマを指定してWebを検索する機能（初版は「決めたサイトの新着を集める」形）
- 新着のポップアップ通知（初版はメニューバーの未読件数表示だけ）【判断】
- 課金・ライセンス認証【決定】
- 複数端末での既読の同期、サーバー【決定: すべてMacの中だけで動く】
- 署名・公証つきの配布（Apple Developer Programへの登録が必要になるため）【判断: 初版は自分のMacでビルドして使う】
- 「今日の3行まとめ」のような、全体を横断する要約【判断: 画面案Bにあった機能で、選ばれたC案には含めない】
- OPML（他のRSSリーダーとの購読リスト受け渡し形式）の読み込み・書き出し【判断: 公開前に検討】

## 4. 失敗とみなすこと（動いていても失敗）【判断: 会話から推測したもの】

- **量が多すぎて読み切れない**: 開いても「今日はこれで終わり」と思えないなら、目的を果たせていない。初期の情報源は1日20件前後に抑える
- **要約が元記事とずれている、またはもっともらしい誤りを含む**: 要約だけ読んで判断する使い方なので、致命的
- **静かに壊れる**: フィードの取得失敗やAPIキーの失効に気づけず、「新着がない」と誤解させる
- **思わぬ費用がかかる**: 初回の取得や情報源の追加のたびに、過去記事を大量に要約してAPI費用が膨らむ

## 5. 制約

- 対象: macOS（ユーザーの開発機はmacOS）
- 言語: Rust【決定】。画面はHTML/TypeScript【決定: Tauriの標準構成】
- アプリの枠組み: Tauri（v2系）【決定】。将来スマホに広げるときも同じ枠組みを使える
- AI要約: 利用者が自分のAPIキーを設定する方式（BYOK）【決定】。運営側のサーバーや費用は発生させない。初版で対応するAIはClaude（Anthropic API）【判断】
- APIキーはmacOSのキーチェーンに保存する。設定ファイルやリポジトリには入れない【決定】
- 情報源: RSS / Atom / RSS 1.0（RDF）のフィードがあるサイトのみ【決定】
- リポジトリ: GitHubの個人アカウント `tei0110` に非公開で作り、公開したくなったら公開に切り替える【決定】
- 後から有料化できる道を残す【決定】。そのための具体策は次の通り【判断: 収益化の形はまだ決まっていないので、どの形にも進めるようにしておく】
  - Mac App Storeでの販売に備え、初版から**App Sandbox内で動く作り**に寄せる。ログイン時の起動は `SMAppService` を使い、データはアプリのコンテナ内に保存する。キーチェーンも、Sandboxで使える方法でアクセスする
  - 将来、運営側がAI要約を代行するサブスクリプションにも対応できるよう、要約のtrait（8.3）は、認証つきの外部サーバーも処理先として差し込める形にする
  - 依存ライブラリは、MIT・Apacheなど制約の少ないライセンスのものに限る（GPL系は避ける）
- コミットのメールアドレスはGitHubのnoreplyアドレス（`41860242+tei0110@users.noreply.github.com`）にする（リポジトリ単位で設定済み）。仕事用のメールアドレスを公開リポジトリの履歴に残さないため【判断】

## 6. 画面と動き【決定: 画面案C「メニューバー型」を選択。細部は以下の通り】

### 6.1 常駐

- アプリはMacのメニューバーに常駐する。Dockにはアイコンを出さない【判断】
- メニューバーのアイコン横に未読件数を表示する
- ログイン時に自動起動する設定を用意する（初期値はオフ）【決定: 2026-11-02 にオンから変更。Mac App Store の審査ガイドラインは、ユーザーの同意なしにログイン時に起動させることを認めていないため。オン・オフは保存せず、macOS の登録状態をそのまま使う】

### 6.2 一覧（アイコンをクリックすると開く小窓）

- 上部: 「新着 N件」、最終更新時刻、手動更新ボタン、設定ボタン
- タブ: 「すべて」と、情報源に付けた分野ラベルごとのタブ（初期は「AI」「セキュリティ」）。タブには未読件数を出す
- 各記事: 日本語タイトル＋一言要約＋情報源名・経過時間。新しい順に並べる
- 下部: 「すべて既読にする」
- 小窓の外をクリックすると閉じる

### 6.2.1 広げて読む画面【決定: 2026-11-04 追加】

- 記事が溜まったときに1件ずつじっくり読むための別ウィンドウ。小窓の「⤢ 広げる」から開く
- 2ペイン: 左に一覧（タブ・すべて既読・既読も表示は小窓と同じ）、右に選んだ記事の詳しい要約と「元記事を開く」
- ↑↓ / j k で前後の記事へ、Enter で元記事を開く。右に表示した記事は既読になる（閉じるまでは ○ で一覧に残す）
- 位置と大きさを覚えて次も同じに開く。開いている間だけ Dock と Cmd+Tab に出す

### 6.3 記事をクリックしたとき

- その場で広がり、2〜3文の詳しい要約と「元記事を開く」ボタンを表示する
- 「元記事を開く」は既定のブラウザで元記事を開く
- 広げた記事は既読になり、未読件数が1つ減る
- 既読にした記事は、小窓を開いている間は既読の印をつけて残し、次に開いたときには一覧から消える。「既読も表示」に切り替えれば見られる【判断】

### 6.4 設定画面（別ウィンドウ）

- 情報源: 一覧（名前・URL・分野ラベル・有効/無効・最終取得結果）、URLを入力して追加（追加時にフィードとして読めるか確認する）、削除
- おすすめの情報源: 7.2の一覧からワンクリックで追加できる
- AI要約: APIキー（キーチェーンに保存）、使うモデル（初期値あり、変更可）、要約の言語（初期値は日本語）【判断: 公開を考えて言語を選べるようにする】
- 自動更新の間隔: 30分 / 1時間（初期値） / 3時間 / 6時間【判断】
- 文字の大きさ: 小窓・広げて読む画面それぞれ 小（90%）/ 標準（100%、初期値）/ 大（115%）/ 特大（130%）。大きくするのは記事の部分（一覧と右側の本文）だけで、ヘッダー・ボタン・タブ・設定画面は固定（2026-11-06 追加。小窓は幅が決まっていて、ボタンまで大きくすると折り返して崩れるため）
- ログイン時に起動: オン/オフ

### 6.5 エラーの見せ方【判断】

- フィードの取得に失敗した情報源は、設定画面の一覧で失敗したことと理由がわかるようにする
- 小窓・広げて読む画面の帯（「一部の情報源を取得できませんでした」）に出すのは、次のどちらかのときだけ（2026-11-06 追加。hnrss.org がほぼ毎日 1 回 502 を返し、帯が出っぱなしになったため）
  - 一時的でない失敗（404・403・フィードとして読めない など）: 1回目から出す
  - 一時的な失敗（通信エラー・タイムアウト・5xx・429）: 同じ情報源で2回続いたら出す。1回目は設定画面にだけ出る
- 情報源ごと・更新ごとの取得の結果（日時・成否・理由・一時的か）を DB の `fetch_log` に残し、30日で消す。設定画面には直近7日の「失敗 N回／M回（最後の失敗 日時 理由）」を出す
- すべての情報源につながらなかった回（オフライン・スリープ明け直後）は、履歴に残さず帯にも出さない。「最終更新」が進まないことで分かる
- APIキーが未設定・無効、または要約に失敗した場合は、小窓の上部に1行で表示する。要約できなかった記事も、タイトルとリンクは一覧に出す

## 8. 新着の取得と要約

### 8.1 取得

- 自動更新の間隔ごとに、有効なすべての情報源のフィードを取得する。手動更新ボタンでも同じ処理を行う
- 記事の同一性は、フィードの記事ID（guid / id）で判定する。IDがなければURLで判定する
- 別の情報源から同じURLの記事が来た場合は1件にまとめる（URLは末尾のスラッシュや追跡用パラメータなどを正規化して比べる）【判断】
- **取り込むのは、常に公開から48時間以内の記事だけ**。初回取得、情報源の追加・再有効化、Macを数日開かなかった後の更新も含め、すべて同じルールにする。不在の間の古い記事は取り込まない。読み切れない量になるのと、過去記事の大量要約で費用が膨らむのを防ぐため【判断】
- 記事は30日で削除する。ただし、一度取り込んだ記事のIDは別に残し、古い記事を長く載せているフィードで過去記事が新着として再び現れないようにする【判断】

### 8.2 要約【判断: 細部】

- 新しく取り込んだ記事ごとに、AIに次の3つを作らせる
  - 日本語タイトル（元が日本語ならそのまま）
  - 一言要約（一覧用。全角30文字程度）
  - 詳しい要約（広げたとき用。2〜3文）
- 元のタイトルも保存しておき、広げたときに小さく表示する
- 要約の材料:
  1. フィードに本文や概要が十分に含まれていれば、それを使う
  2. 足りなければ（Hacker Newsなど）、記事のURLを取得して本文を抽出する。サイトごとの個別ルールは作らず、汎用的な本文抽出だけを行う
  3. それでも本文が取れなければ要約せず、タイトルとリンクだけを表示する
- AIに渡す本文には長さの上限を設けて、費用を抑える
- 1回の更新で要約する件数にも上限を設ける。上限を超えた分は次の更新で要約する
- 要約は取得時にバックグラウンドで作っておき、小窓を開いた瞬間に読める状態にする
- 誤った要約を防ぐため、プロンプトでは「本文に書かれていないことは書かない」ことを明示する

### 8.3 AIの呼び出し

- Anthropic Messages APIをRustからHTTPで直接呼ぶ
- 将来ほかのAIサービス（OpenAI互換のAPIやローカルLLMなど）を足せるように、要約処理は差し替え可能な形（Rustのtrait）にしておく【判断】。初版で実装するのはClaudeだけ
- 初期のモデルには、Claudeの小さく速いモデル（Haikuクラス）を使う。具体的なモデルIDは、実装時点の最新ドキュメントで確認する【判断】

## 9. 技術構成【判断: 「アプリの中身はRust、画面はTypeScript」は決定済み。分け方は設計者の判断】

- **Cargoワークスペースを2つのクレートに分ける**
  - `core`（名前は実装者に任せる）: フィードの取得・解析、新着判定、保存、本文抽出、要約、更新のスケジュール。Tauriに依存させない
  - `app`: Tauriのアプリ本体。メニューバー、小窓、設定画面、`core`の呼び出し
  - 分ける理由は3つ。テストしやすい、スマホ版で`core`を使い回せる、ポートフォリオとして設計の意図が伝わる
- 判断や処理（新着判定・既読管理・件数計算など）は、すべてRust側に置く。TypeScript側は、Rustから受け取った状態を表示して操作を伝えるだけにする。Rustの学習量を増やすためでもある
- 保存: SQLite（記事、情報源、既読状態、要約）
- 設定値: SQLiteかTOMLファイル（実装者に任せる）。APIキーだけはキーチェーンに保存する
- 画面のTypeScriptフレームワークは実装者に任せる。小さな画面2つなので、軽いもので十分

## 10. 品質とポートフォリオ【判断】

- テスト: `core`の単体テストを中心に書く。対象は、各形式（RSS 2.0 / Atom / RSS 1.0）のフィード解析、新着判定、URLの正規化と重複除去、48時間ルール、要約件数の上限。テスト用のフィードは、7章のサイトから取ったサンプルをファイルとして置く。要約のAPI呼び出しはモックにする
- GitHub Actions: `cargo fmt --check`、`cargo clippy`、`cargo test`
- README: 何をするアプリか、スクリーンショット、構成図、ビルド手順、APIキーの設定方法、おおよそのAPI費用の目安

## 12. 実装の進め方と分担【決定】

Rustの勉強とポートフォリオ（自分の言葉で説明できること）を両立させるため、中心部分はユーザー本人が書き、周りはClaudeが書く。

- **Claudeが書く**: Tauriアプリの枠組み、メニューバーと小窓、設定画面、画面とRustの橋渡し（Tauriのコマンド）、GitHub Actions
- **ユーザーが書く**（`core`クレートの中心部分。この順番で進める）
  1. フィードの取得と、記事のデータへの変換
  2. 保存と新着の判定（48時間ルール、重複除去、既読管理）
  3. AI要約（要約のtraitと、Claudeを呼び出す実装）
  4. 記事ページからの本文抽出
- 各段階の進め方:
  - Claudeが先に、完成したら通るテストと、関数・型の形（シグネチャ）を用意する
  - ユーザーが、テストが通るように中身を書く
  - 書き終えたら、Claudeがレビューする
  - 行き詰まったときや時間がないときは、その段階だけClaudeが引き取れる
- ユーザーが書く部分でも、フィードの解析、HTTP、SQLiteなどの土台にはクレートを使う。これらを自作することまでは求めない【判断】
- 段階2が終わった時点で、「新着のタイトルとリンクがメニューバーに並ぶ（要約はまだない）」状態にして、使い始められるようにする。そのため、Claudeが担当する画面側は、段階2の完了に間に合わせる【判断】

## 13. 実装者に任せること（上の分担に従い、担当する側が決める）

- 使うクレート（HTTPクライアント、フィード解析、SQLite、キーチェーン、本文抽出など）の選定
- 小窓の正確なサイズ、位置、見た目
- 要約プロンプトの具体的な文面と、本文の長さ・1回あたりの要約件数の上限値
- 複数の記事をまとめて1回のAPI呼び出しで要約するかどうか
- スリープ復帰時にすぐ更新するかどうか
